# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> All user-facing copy is Spanish (es-MX). The app is single-locale; no i18n framework. Static strings go in `src/lib/copy/es.ts`, interpolated sentences in `src/lib/copy/messages.ts`, money and dates in `src/lib/format.ts`.
>
> This phase **extends** `01-UI-SPEC.md`, `02-UI-SPEC.md` and `03-UI-SPEC.md` (all approved). Tokens, the 4 type sizes, the 2 weights, the spacing scale, theme behavior, top bar, the 44px touch-target rule, the Tooltip / tap-Popover rule for truncated text, the "Deshacer" toast rule (6 s, bottom-right, closable), the inline-rename pattern, the `AlertDialog` focus rule and the accessibility floor stay in force and are **not repeated** unless this phase adds to them. "As Phase 3" means follow the Phase 3 contract exactly. The new tab must look like the same app: same bordered `background` blocks, same 20/600 headings with a 12px muted intro, same row captions.
>
> Source key: **[D-nn]** = locked decision in 04-CONTEXT.md (decisions of earlier phases are cited as **[P1 D-nn]**, **[P2 D-nn]**, **[P3 D-nn]**). **[P1]** / **[P2]** / **[P3]** = rule inherited from that phase's UI-SPEC. **[CLAUDE.md]** = stack decision locked by the user. **[RESEARCH]** = fact or constraint from 04-RESEARCH.md ("UI-relevant constraints", latency estimates, error taxonomy). **[default]** = low-risk value chosen by the researcher because no upstream artifact answers it (listed under "Defaults taken"). **[user-confirmed OQn]** = decision the user locked on 2026-10-19 by answering open question n (recorded under "Resolved with the user"; do not re-ask).

## Spacing Scale

Same scale as Phases 1 to 3 (multiples of 4; Tailwind 1 unit = 4px): xs 4 · sm 8 · md 16 · lg 24 · xl 32 · 2xl 48 · 3xl 64. Usage in this phase:

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| xs | 4px | Icon-to-text gap, gap between a description and its caption, gap between a Select and its caption |
| sm | 8px | Gap between card action buttons, between member rows' inner items, filter toggles, bulk-bar buttons |
| md | 16px | Queue card padding, gap between queue cards, gap between the two title-row buttons' columns, dialog inner padding |
| lg | 24px | Padding of the bordered section blocks ("Mis productos", suggestion table), run card vertical rhythm |
| xl | 32px | Gap between the sections of the Productos tab, between tab list and panel |
| 2xl | 48px | Empty-state vertical padding |
| 3xl | 64px | Page bottom padding |

Exceptions (all multiples of 4, outside the 7-step scale on purpose):

- Everything listed as an exception in Phases 1 to 3 stays (top bar 56px, `max-w-6xl` 1152px, 44px touch targets under 640px, table row 40-56px, 288px list max height, tab list 44px under 640px).
- Title-row buttons: 36px tall (44px under 640px, full width each).
- **Send / privacy dialog:** `AlertDialog` widened to 560px (`sm:max-w-[560px]`, full width minus 32px under 640px) because it carries the literal list; the list lives in a `ScrollArea` of max 288px. Other dialogs (bulk-accept confirmation) keep the shadcn default (384px).
- Queue column: `max-w-[880px]` (cards are text-heavy; the other sections use the full container width). Queue card padding 16px; name `Input` height 36px (44px under 640px); member row min height 44px; card action buttons 36px (44px under 640px).
- "Unir con…" / "Mover a…" popover: width 320px (full width of its trigger under 640px), list max height 288px, items 36px (44px under 640px). Same width as the category filter popover.
- Suggested-category table: min width 760px inside `overflow-x-auto` (the page never scrolls horizontally); row min height 56px; Select trigger width 240px (full width of its cell under 640px); actions column 220px.
- "Mis productos" table: row min height 56px; table min width 880px inside `overflow-x-auto`; Select trigger width 240px; actions column 96px; the expand column 48px.
- Run card: same padding as `ProcessingIndicator` (`gap-3 px-4`); Progress bar 8px tall; the "Detener lotes" button 36px (44px under 640px) on the right of the first line (wraps under the text below 640px).
- Concept category Select: the "del producto" suffix block is capped at 120px for the product name (see Layout → Concept panel); trigger min width stays 240px.
- Tab list: five triggers; the list keeps the Phase 3 behavior (horizontal scroll under 640px, 44px height).

## Typography

Exactly the Phase 1 set: **4 sizes and 2 weights**. Nothing new. The 28px display size is not used in this phase.

| Role | Size | Weight | Line Height | Used in this phase for |
|------|------|--------|-------------|------------------------|
| Body | 14px | 400; 600 for buttons, labels, tab triggers, product names (card header, accepted list), table headers, run-card status text | 1.5 | Descriptions, product names, table cells, Select values, dialog body and dialog list rows, toasts, inputs |
| Label / caption | 12px | 400 (600 for table column headers) | 1.5 | Supplier name and line count under a member, section intros, counts, button captions ("227 descripciones sin agrupar"), "Sin líneas cargadas", "Nueva", helper and error text, the "· del producto …" suffix, run-card caption |
| Heading | 20px | 600 | 1.2 | "Productos", "Sugerencias de productos", "Sugerencias de categoría", "Mis productos", dialog titles |
| Display | 28px | 600 | 1.2 | Not used in this phase |

Rules (additions):

- Counts and line counts use `tabular-nums`. Descriptions and product names are user/vendor data: they wrap and are never truncated in cards, dialogs and the send list (as Phase 3 long-text rule); they truncate only inside a table cell or a Select trigger, with `TruncatedText` or the full name visible when the Select is open.
- Descriptions are vendor-controlled text: render only as React text (never HTML), keep original case (many are uppercase abbreviations), do not "prettify" them. Only the **proposed product name** is expected to be readable Spanish.
- No other sizes or weights anywhere in the phase.

## Color

**No token is added or changed.** The Phase 2/3 tokens (`background`, `secondary`, `border`, `muted-foreground`, `primary`, `destructive`, `--chart-1`) cover everything. Suggestions have **no** special hue: a pending card is distinguished by structure (bordered card with actions), not by a tinted fill.

| Role | Light | Dark | Usage in this phase |
|------|-------|------|---------------------|
| Dominant (60%) `background` | `#FFFFFF` | `#0A0A0A` | Page, queue cards, section blocks, dialogs, popovers |
| Secondary (30%) `secondary` | `#F5F5F5` | `#171717` | Top bar, table header rows, row hover, expanded member panel, queue bulk bar, filter toggle (off state), `Badge` fills |
| Accent (10%) `primary` | `#171717` | `#E5E5E5` | See reserved list |
| Destructive | `#E7000B` | `#FF6467` | See reserved list |
| Muted foreground | `#525252` | `#A3A3A3` | Captions, supplier names under members, "del producto" suffix, "Sin categoría" implicit value, intro text, "Nueva" badge text |

Contrast: only pairs already approved in Phases 1 to 3 are used (muted on background 7.8:1 / 7.8:1, muted on secondary 7.2:1 / 7.1:1, destructive on background 4.8:1 light). Rule kept: destructive text and icons sit on `background`, never on `secondary`.

Rules:

- 60/30/10: the Productos tab sits on `background`; headers, hover, expanded panels, the bulk bar and badges on `secondary`; accent stays small.
- **"Rechazar" is not destructive.** It is a `ghost` neutral button: rejecting only discards a suggestion (and offers "Deshacer"); nothing the user owns is lost. Destructive color stays out of the queue entirely.
- Origin text "· del producto …" in the concept Select uses `muted-foreground`, like "· del proveedor" [P3].

Accent reserved for (Phase 3 list, items 3 and 6 extend to this phase; **item 7 is new**; nothing else):

1. Primary buttons: "Entrar", "Seleccionar archivos", "Agregar facturas" (still the only accent-filled button on any **non-modal** screen; "Agrupar productos", "Sugerir categorías", "Aceptar", "Unir con…", "Detener lotes" and every other button in this phase are `outline` or `ghost`).
2. Dropzone drag-over state and the window drop overlay border.
3. Progress bar fill (now also the "Lote N de M" bar).
4. The active sort icon in any table header (including "Mis productos").
5. The 2px keyboard focus ring on all focusable elements.
6. The 2px underline of the active tab (now five tabs) and the single bar under the pointer in the monthly chart.
7. **New [default]:** the confirm button of the two modal `AlertDialog`s of this phase, **"Enviar a DeepSeek"** and **"Aceptar {n} sugerencias"**. While a modal is open the page behind is inert, so each is the only filled button in view. They are the two deliberate "go" actions of the phase (data leaves the browser; many suggestions are applied at once), so they earn the one filled button.

Destructive reserved for (Phase 3 list plus one icon):

1. Confirm buttons of "Cerrar sesión" and "Quitar todas" (P1); the login error text and the "Rechazados" value/icon (P1).
2. "Borrar categoría" confirm and "Reemplazar mis ajustes" confirm (P3), and the `CircleAlert` icon of the invalid-backup Alert (P3).
3. **New:** the `CircleAlert` icon (not the text) of the run-failure and run-stopped Alerts. Their message text is `foreground`.
4. Nothing else: "Borrar producto", "Rechazar" and "No agrupar" are reversible with "Deshacer" and use neutral buttons.

## Layout & Interaction Contract

### Primary focal point per screen

### Shell and tabs [D-01]

- Five tabs; `AppTab` gains `"productos"`; `isAppTab`, `TABS` and the `TabsContent` list in `AppShell.tsx` and `es.tabs.products` are extended. Same trigger styling (14/600, 40px list, accent 2px underline). Position after "Categorías" **[user-confirmed OQ4]**.
- The trigger shows " · {n}" when n > 0 (pending product cards + pending category rows), like "Calidad de datos", with the accessible name from the copy table.
- The five triggers must not wrap; the Phase 3 behavior stays (under 640px the list scrolls horizontally, the active trigger is scrolled into view). **The verification run must check 640 to 767px**, where five triggers with two counters are tight; if they overflow the container there, the list scrolls (`overflow-x-auto`) at that width as well.
- The run keeps going if the user switches tab (the run lives in a non-persisted store [RESEARCH Pattern 2], the panel unmount does not abort it). When it finishes while another tab is active, the end-of-run toast offers «Revisar».

### Productos tab composition

Vertical order, 32px gaps: (1) title row, (2) Alerts present (settings write failure, pending-store write failure, run result / failure / stopped / canceled), (3) run card while a run is active, (4) "Sugerencias de productos", (5) "Sugerencias de categoría", (6) "Mis productos", (7) «No agrupar» collapsible. Sections (4), (5) and (7) are not rendered when empty. When there is no accepted product, no pending suggestion and no «No agrupar» mark, sections (4) to (7) are replaced by the `Empty` state (the entry buttons stay).

**Title row (1):** left, Heading "Productos" with the two intro lines (12px muted). Right (wraps below the heading under 768px, each button full width and 44px under 640px): two columns, each a button (`outline`, 36px, icon 16px) with its 12px muted caption underneath. Buttons are never disabled with `disabled`; see Copywriting (`aria-disabled`).

**Source of the data [D-03, D-04]:** the free set and the counts in the captions are computed from **all loaded invoices** (the unfiltered ledger), regardless of Dashboard filters, exclusions or whether the invoice counts. **Every concept type is included [user-confirmed OQ2]**: tipo P ("Pago") and tipo E (credit notes) are sent like tipo I, so the captions and dialog counts include them (the sample has 227 distinct items, one of them the payment-complement concept «Pago»). No exclusion copy exists.

### Send flow and dialog [D-08, LLM-06]

1. Press the entry button. If nothing is free, nothing opens (caption already says so).
2. The send dialog opens. The summary and the list are generated from **the very object that will be serialized as the request body** (what you see is what is sent; RESEARCH Pattern 4). If a run needs M batches, the dialog covers the whole run (N items, "Se enviarán en M lotes.").
3. «Enviar a DeepSeek» closes the dialog, starts the run and moves focus to the run card's «Detener lotes» button. «No enviar» (or Esc) closes it and sends nothing; focus returns to the entry button.
4. The disclosure («Ver exactamente qué se envía») is a `Collapsible` closed by default, `aria-expanded`; content in a `ScrollArea` (max 288px), grouped as in the copy table, each group with its heading. Long lists scroll inside the dialog; the dialog itself never exceeds the viewport (max height viewport minus 32px, content scrolls).
5. Under 640px the dialog buttons stack (primary last), 44px tall.

### Run card [D-26, D-27, LLM-05]

- Appears in position (3) as soon as a run starts and stays until it ends. States: **running**, **cancelling**, **finished** (card disappears, toast), **finished with failures** (card disappears, partial-failure Alert), **stopped** (non-retryable condition, Alert), **canceled** (Info Alert).
- The Progress bar fill = completed batches ÷ M (accent, 8px, `aria-label` "Progreso de los lotes", `aria-valuenow/min/max`). A request is not streamed, so there is no intra-batch progress: the Spinner beside "Lote {k} de {M}" shows that the current batch is in flight. With M = 1 the bar stays at 0 until the response lands (the Spinner and the caption carry the feedback); **no indeterminate animation is added**, so nothing needs a reduced-motion fallback.
- The status text container is `aria-live="polite"` and `aria-atomic="true"`; it updates when a batch starts or ends, at most once per batch.
- «Detener lotes» is enabled the whole time. Pressing it sets "Deteniendo…" (inert, `aria-busy`), stops later batches, keeps what already arrived, and ends in the canceled Alert. Nothing from the cancelled batch is enqueued.
- The two entry buttons are `aria-disabled` while a run is active (single run slot).
- A batch that fails shows nothing while the run continues; failures are summarized at the end ("{n} lotes fallaron · Reintentar") with the last reason underneath. A non-retryable condition stops the run after that batch with the stopped Alert (no further batches are sent).
- Clearing all invoices ("Quitar todas") while a run is active cancels the run **[default]**; pending cards stay.

### Queue of product suggestions [D-19..D-22, D-25]

- **Order [default]:** "Agregar a" cards first, then groups with several members (members descending, then total lines descending), then singletons (lines descending, then name `es`). New batches append in this order; the position of cards the user is working on does not jump while a run is in progress (new cards are inserted only below the last card already shown, then the list re-sorts on the next filter or page change).
- **Filter bar:** search `Input` (36px, 320px wide, full width under 640px) and a `ToggleGroup` (single selection, "Todas" default). Both narrow the list; the counts in the toggles are over all pending cards.
- **Bulk bar [D-20]** (a `secondary` row: select-all checkbox "Seleccionar visibles", the selected count, "Aceptar seleccionadas", "Rechazar seleccionadas", and "Aceptar todas las visibles" at the right; wraps on narrow widths). "Visibles" = every card matching the active filter and search, including cards not yet shown by "Mostrar más" **[user-confirmed OQ6]**; the confirmation dialog states the exact count, so the user always sees how many will be created. "Aceptar seleccionadas" has no confirmation (the user picked each card) [default]. The page does nothing without one of these explicit actions.
- **Cards:** a `<ul>` of `<li>` cards, 16px gaps, 50 shown at first, «Mostrar {n} más» below. Card layout:
  - header row: card checkbox (bulk) + name `Input` (the proposed name, editable in place, 60 max, Enter or blur commits to the pending suggestion; errors under the input) + member count caption right-aligned ("3 descripciones"; singletons show no count);
  - member rows (min 44px): member checkbox, description (wraps), 12px muted caption "{proveedor} · {n} líneas" or the «Sin líneas cargadas» Badge, and the `Ban` icon button "No agrupar esta descripción" at the right;
  - footer row: **Aceptar**, **Rechazar**, **Unir con…**, **Separar en producto nuevo** (`outline`/`ghost` as in the copy table; the last is enabled only when some but not all members are checked). A singleton card has no member checkbox and no "Separar".
- **"Agregar a «X»" card [D-21]:** same card without the name input; the title is "Agregar a «X»", only the new members are listed with checkboxes, actions are Aceptar, Rechazar and "Separar en producto nuevo". Accepting adds the checked members to the product without touching its existing members or category; unchecked members stay in the card.
- **Aceptar:** validates (unique name `comparableName` vs. accepted products, not reserved, product limit, members not already taken). On error the card stays and shows the error under the field or under the footer (role `alert` is not used; the message is linked with `aria-describedby`). On success the product is created in the settings store (members = rfc + normalized description + readable description + supplier name [D-09]), the card leaves the queue, the toast shows, and **focus moves to the next card's name input** (to the section heading when it was the last).
- **Rechazar [D-22]:** the card leaves, its descriptions stay free, the toast offers «Deshacer».
- **Unir con… [D-19]:** a `Popover` + `Command` listing the other pending cards (name + member count) and the accepted products. Choosing a pending card moves this card's members into it and removes this card; choosing an accepted product turns this card into an "Agregar a «X»" card (nothing is applied until «Aceptar»). Toast «Deshacer» in both cases.
- **Separar [D-19]:** checked members leave the card and become a new pending card named after the first checked member's description (cut to 60), placed right below, focus on its name input. Toast «Deshacer».
- **No agrupar esta descripción [D-22]:** the member leaves the card (the card disappears if it was the only member), the mark is stored in the settings, toast «Deshacer».
- Cards render without invoices loaded (the tab is hidden then, but a user who reloads and loads only a few files sees members with «Sin líneas cargadas»).
- Mobile: the card footer buttons wrap, 44px tall; member rows stack the caption under the description.

### Category suggestions table [D-17, D-18, D-23]

### Persistence contract (UI-visible parts) [D-13, D-24]

- Accepted products and «No agrupar» marks live in `invoicechecker:settings` (version 3) and in the backup file (file version 2); a v2 settings payload and a v1 backup file keep loading with empty products. The backup is the only place the user can take products to another browser.
- Pending suggestions live under their own key, never in the backup file. The Productos intro says so (copy above).
- Run state, progress and the id map are in memory only; a reload during a run loses only the in-flight batch.
- Every storage call stays in `try/catch`; failures use the storage notices above.

### Accessibility floor (additions)

- Tabs: five triggers with roving arrow keys, `aria-selected`; the counter is in the accessible name.
- Dialogs: `AlertDialog` focus lands on the dismiss button; Esc dismisses; the accent button is last; the disclosure is operable by keyboard and the list is reachable with Tab inside the `ScrollArea`.
- Cards and rows are lists with real buttons; every icon-only button has `aria-label` and Tooltip with the same text and **names the description or product it acts on**; bare "Aceptar" buttons inside a card carry `aria-label` "Aceptar la sugerencia «{nombre}»" (and "Rechazar…" the same way), so a screen-reader list of buttons is unambiguous.
- Checkboxes have labels naming the item; the bulk-bar checkbox uses `aria-checked="mixed"` when only some visible cards are selected.
- Forms: the name input uses `aria-invalid` + `aria-describedby`; focus moves are specified for accept, reject, rename, delete and run start.
- Live regions (polite): run status, queue counts after accept/reject, "Marca quitada". Toasts with actions stay 6 s and are keyboard reachable [P2].
- Transitions 150 ms, removed under `prefers-reduced-motion`; the Progress `transition-all` is disabled under reduced motion. No new animation is introduced.
- Contrast: AA in both themes per the Phase 1 to 3 tables; destructive text only on `background`.
- Vendor descriptions are untrusted: React text only, no `dangerouslySetInnerHTML`, no markdown rendering (RESEARCH Pitfall 7).

## Defaults taken (low-risk, not asked; listed so the checker and planner can see them)

- Entry buttons are `outline`; the only accent-filled buttons of the phase are the confirms of the two modal dialogs (accent list, item 7).
- Each entry button has a visible 12px caption with its count; a disabled entry button uses `aria-disabled` and keeps focusable (as the export button of Phase 3).
- Queue: order (Agregar a, then several members, then singletons), 50 cards per page with "Mostrar {n} más", filter toggles and search, single column `max-w-[880px]`, a new batch never reorders cards already shown.
- "Aceptar seleccionadas" and "Rechazar seleccionadas" apply without a confirmation (the user picked the cards); "Rechazar", "Unir" and "Separar" offer «Deshacer».
- A successful accept shows a toast; focus moves to the next card (heading when last).
- A name proposed when separating is the first checked member's description, cut to 60 characters; product name maximum 60 characters (same as category names, RESEARCH A11).
- "Mis productos": default sort by name (`es`), 50 per page, several rows can be expanded at once, delete and member actions apply at once with «Deshacer», no destructive dialog.
- Category suggestion table: suppliers before products, each alphabetical; "Sin categoría" is not offered in its Select.
- The end-of-run toast, the tab counter " · {n}" and the «Revisar» toast action.
- Clearing all invoices during a run cancels the run (RESEARCH Open Question 13, recommended).
- No indeterminate progress animation: the bar shows completed batches and a Spinner marks the one in flight.
- Not UI (listed so nobody asks twice): whether the pending-suggestions store keeps the supplier RFC (RESEARCH Open Question 1, recommended: yes, it never leaves the browser). It changes nothing the user sees.

Confirmed upstream (do not re-ask): everything in 04-CONTEXT.md D-01..D-28 and in the Phase 1 to 3 UI-SPECs (Geist fonts, neutral accent, light/dark, 44px touch targets, Tooltip + tap Popover for truncated text, 150 ms transitions, confirmation dialogs, Deshacer toasts of 6 s).
