## Phase Goal

**As a** dueño, socio o contador del Coworking Café, **I want to** pedir a DeepSeek que agrupe como "mismo producto" los conceptos con descripciones distintas entre tiendas y que sugiera categorías, revisando cada sugerencia antes de aplicarla, **so that** nada cambia sin mi revisión y a DeepSeek solo llegan descripciones de conceptos y nombres de proveedor, por una ruta protegida.

<objective>
Let DeepSeek add new descriptions to products the user already has: product names go as context (D-04), groups placed with an accepted product become «Agregar a «X»» cards (D-21), and runs of several batches can join descriptions across batches (D-28).

Purpose: without context every new invoice upload would create duplicates of products the user already curated. Which names go as context is ambiguous across D-04, D-25, D-28 and the approved dialog copy, so the plan asks first (CLAUDE.md rule 1).
Output: the user's choice, context-aware bodies and target map, the in-run join rule, `addMembersToProduct`, the context lines of the dialog and the «Agregar a» card.
</objective>

  <name>Task 1: Which product names travel as context with «Agrupar productos»</name>
  <decision>Which names go in the existing list of the grouping requests, and what happens when DeepSeek places a new description with one of them</decision>
  <context>
    D-04 says the names of accepted products go as context «(y de los sugeridos en lotes previos, D-25)»; D-25 says pending suggestions are not touched when the button is pressed again; D-28 says each later batch of one run receives the names suggested in the earlier batches «para que descripciones parecidas en lotes distintos se puedan unir»; the approved UI-SPEC line 198 says «Como contexto también se enviarán {n} nombres de productos que ya aceptaste» and the dialog must list exactly what is sent. These do not settle whether the names of suggestions still pending from an earlier press are sent. The choice is cheap to change later (rated reversible); it only decides what this plan writes. The real sample fits in one batch, so the in-run part matters only above the batch limit.
  </context>
  <options>
    <option id="option-a">
      <name>Accepted names at send time, plus earlier-batch names inside one run (recommended)</name>
      <pros>Matches the approved dialog line word for word. Pending cards from earlier presses are never changed (D-25). Inside one long run, a later batch can join a description to a card of an earlier batch (D-28): it is appended while that card is pending, becomes an «Agregar a» card if the user accepted it meanwhile, or keeps its own card if the user rejected it. The batches line gains the sentence «Cada lote lleva también los nombres que DeepSeek propuso en los anteriores.» so the extra names, which are DeepSeek's own output, are disclosed.</pros>
      <cons>A description sent in a later press that matches a pending card of an earlier press gets its own card; the user joins them with «Unir con…» (Plan 04-12).</cons>
    </option>
    <option id="option-b">
      <name>Also send the names of every pending suggestion</name>
      <pros>DeepSeek sees everything already proposed and can point new descriptions at pending cards from earlier presses.</pros>
      <cons>The approved dialog line must change to «…nombres de productos que ya aceptaste o que están por revisar» and list them; a new description placed with an old pending card either changes that card (D-25 says pending cards are not touched) or needs a new kind of card.</cons>
    </option>
    <option id="option-c">
      <name>Accepted names only, no names between batches</name>
      <pros>Simplest; the dialog lists exactly what every batch sends.</pros>
      <cons>D-28's cross-batch joining is lost for runs above the batch limit; those pairs need «Unir con…».</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b or option-c (or describe changes)</resume-signal>
